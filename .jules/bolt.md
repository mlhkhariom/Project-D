## 2026-02-26 - [Global View Composer Performance Trap]
**Learning:** Services injected via `View::composer('*')` execute for *every* partial view rendered (including components and includes). Without memoization, this causes severe N+1 query issues (e.g., 12 queries instead of 2 for a simple page). `Schema::hasTable` in SQLite queries `sqlite_master` and is not automatically cached by Laravel.
**Action:** Always audit global view composers for database calls and ensure strict memoization (property caching) in the service layer. Use `DB::enableQueryLog()` in feature tests to assert query counts.
## 2026-03-20 - [Singleton Service Initialization Optimization]
**Learning:** Procedural generation of large arrays in singleton constructors (like `ThemeService`) adds significant initialization overhead, especially when those singletons are eagerly loaded or resolved multiple times (despite being singletons, e.g. during tests). The use of functions like `array_rand()` in constructors can also lead to non-deterministic behavior and bugs. Hardcoding static data directly into class properties allows PHP's OPCache to store and serve the data from shared memory, eliminating initialization CPU cycles entirely.
**Action:** Always prefer statically defined data structures over procedurally generated ones for static/configuration data. Audit singleton constructors for expensive operations and move them out or pre-calculate them.
